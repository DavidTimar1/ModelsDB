# ModelsDB - Agent Rules

A single-binary Go web app for browsing, rating, and annotating AI models. The catalog comes from OpenRouter and is enriched by scraping its collection pages. Read these before non-trivial work: **`README.md`** (overview, setup, usage, query API), **`ARCHITECTURE.md`** (backend and data design), and **`DESIGN.md`** (UI/CSS/JS choices). This file holds only the project-specific rules. It does not repeat what those cover.

## Working rules

- Target Go 1.26+ (any newer 1.x). Nothing is pinned to an exact Go or module version, so fix forward if an update breaks the build. Verify every change with `go build ./...`, and run `go run ./cmd/modelsdb` when behavior changes. The frontend is embedded via `//go:embed`, so you must **restart** a running server for it to pick up any `index.html` or `static/` edit.
- Keep changes scoped to existing patterns. The code is split into responsibility packages under `internal/`, wired as a strict import DAG: `paths` -> `shared` -> `dbcore` -> `store` -> `catalog` -> `app` (see ARCHITECTURE.md). Upstream-schema knowledge stays in the `catalog` package. Change the OpenRouter API shape only in `NormalizeModel()` (`internal/catalog/update.go`), and collection mapping only in `collectionDefs` (`internal/catalog/collections.go`).
- Versioning: every commit bumps the `VERSION` file (semver) and adds a matching dated entry to `CHANGELOG.md` in the same commit. Use a patch bump for ordinary changes and minor or major for larger ones.

## Data durability (do not break)

- Paths resolve at runtime into separate **config**, **data**, and **cache** dirs (see `internal/paths/paths.go` and ARCHITECTURE.md). Under `go run` (development) all three collapse onto `./data`, so the rules below read as `data/...` for day-to-day work. In a shipped binary they map to OS-standard dirs.
- `modelsdb.db` (SQLite, in the data dir) is the **single source of truth for ALL model data, objective and personal**, and is git-ignored. On a save or refresh the app exports one human-readable file, `curated.json`. **Personal data is never written to any file.** Back it up by copying `modelsdb.db`.
- `curated.json` (in the data dir, **git-ignored**) is the OBJECTIVE subset only, wrapped in a schema header `{schema_version, min_app_version, models:[...]}`. It holds the full identity and metadata of non-API models plus the curated facts `tool, moe, parameters, active_parameters, disk_size_gb, measurement, pricing_note`. It is a one-way export of the DB, because you cannot git-track the binary DB and the DB contains personal data that must not be published. It is also what an EMPTY DB seeds from if it happens to be present in the data dir. Bump `CuratedMinAppVersion` (in `internal/shared/version.go`) only when a change makes the catalog unreadable by older builds.
- The **PUBLIC catalog ships embedded in the binary** at `internal/seedcatalog/catalog.json` (`//go:embed`). A fresh install seeds an empty DB from that embedded copy on first launch, offline (`store.ImportCuratedBytes`, `EnsureSeeded`). This committed file is the single published catalog; `data/curated.json` is no longer git-tracked. Publish a new catalog with `modelsdb export internal/seedcatalog/catalog.json` (the `export` CLI writes the objective catalog, **excluding personal data and `unlisted` models**), then commit and build the release. `build.sh` auto-refreshes this file from the live DB when one is present. A model flagged **`unlisted`** stays in the DB but is withheld from every export.
- **Personal fields** (`notes, speed, rating, favorite, ocr_quality`) live ONLY in the DB. There is no `personal.json`. Objective pricing caveats belong in `pricing_note` or `measurement`, NEVER in `notes`.
- **The DB is authoritative. `curated.json` is a derived export. STARTUP MUST NOT OVERWRITE `curated.json`.** These invariants are deliberate. Do not "improve" them back:
  - *Startup is read-only for `curated.json`.* The automatic startup fetch (`catalog.FetchModels`) refreshes the DB but does NOT export. Never reintroduce an export there. Startup seeds an EMPTY DB from a data-dir `curated.json` if one exists, else from the embedded catalog; via `store.ExportMissing` it CREATES the data-dir `curated.json` if absent. That is fresh-install materialization, never an overwrite.
  - *The DB wins.* The seed (embedded catalog, or a data-dir `curated.json`) only ever populates an EMPTY DB. On a populated DB, a differing restored `curated.json` is NOT auto-imported, because that would clobber the DB. To roll back, replace `modelsdb.db` (it is migrated forward on open) or clear it and restart so the seed rebuilds it. The `min_app_version` gate applies on that seed: an older build refuses a newer catalog and leaves the DB intact. Migrate forward, never wipe.
  - *Do NOT reintroduce a `personal.json`* or any personal-data export. Personal data stays in the DB, and the durable backup is the DB file. Regression tests: `TestPersonalDataStaysInDBNeverExported`, `TestPopulatedDBKeepsDBAuthoritative`, `TestExportMissingCreatesCuratedOnly` in `internal/app/seed_test.go`.
  - `curated.json` is rewritten ONLY by a real data change: an in-app save (`/api/save`), a user-run update (the "Update models" button or the `update`/`collections`/`pricing` CLI), or the `export` CLI.
- Identity and metadata columns are refreshed from OpenRouter. Never hand-edit them. Curated columns are never auto-overwritten by a refresh.
- **Schema changes go through `internal/dbcore/migrate.go`.** Bump `schemaVersion` by one and append a migration. Never hand-edit `schemaSQL` (in `internal/dbcore/db.go`) for an existing column without a migration. Migrations are transactional, integrity-checked, auto-backed-up (to `<data>/.backups/`), and auto-restored on failure. Do not bypass this path.
- Never commit `modelsdb.db` (it holds your personal data), `*.db-wal`/`-shm`, `.backups/`, `modelsdb.pid`, `config.jsonc`, `settings.json`, `update-check.json`, or `logs/`. The whole `data/` dir is git-ignored; the public catalog lives only at `internal/seedcatalog/catalog.json`.

## Changing model data

Follow the project skill `.claude/skills/update-database-manually/SKILL.md` BEFORE editing model data. It is the authoritative procedure. The API already prices most models. Only API-absent models (and parameter counts) need manual scraping, where the units differ (per image vs per second vs per 1M tokens).

Keep that skill in sync with reality. For ANY change - data model, pricing/curated fields, the update or save flow, or the UI that surfaces curated data (the Unit-cell pricing-note badge, column names, editors) - check `.claude/skills/update-database-manually/SKILL.md` and update it in the SAME change if the change makes anything it describes stale. The skill is public (mirrored to the repo), so a drifted instruction or wrong UI label ships to users.
